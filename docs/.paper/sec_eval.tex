\section{Empirical Evaluation}
\label{sec:eval}

This section presents an empirical evaluation of MAgHARCM on four open-source benchmark repositories. We investigate translation effectiveness, multi-run stability ($K{=}3$), execution latency, per-iteration convergence dynamics, agent ablations, and the root-cause distribution of observed failures.

\subsection{Experimental Setup}
\label{sec:eval_setup}

All experiments were conducted on a Linux workstation with an Intel Core i7-12700H CPU (14 cores, 20 threads), 32\,GB DDR5 RAM, and an NVIDIA GeForce RTX GPU. Local inference executed through Ollama with GPU layer offloading.

To maximise reasoning accuracy within local hardware budgets, MAgHARCM uses a two-tier local model topology. The Analyzer and Planning agents employ \texttt{qwen3:30b-thinking} (Qwen3 30B with thinking-reasoning capability)~\cite{p21_qwen2_5coder,p41_qwen_moe} for repository structural analysis, reverse-topological DAG construction, and cycle elimination. The Translator and Validator agents employ \texttt{Qwen3-4B-Instruct-UD-Q4\_K\_XL}~\cite{p18_deepseekcoder,p22_starcoder2} for Rust syntax synthesis and test-assertion repair. Model selection is fixed in the YAML config and the harness refuses to start without it; there are no in-code defaults that could mask a misconfiguration.

Previous benchmarks enforced an arbitrary 900-second timeout that aborted multi-round repair loops before convergence. In our evaluation we remove that limit: every iteration proceeds until validation succeeds, the coverage plateau detector signals stagnation, the adversarial weakening guard fires, or the maximum iteration limit ($K{=}20$) is reached.

Compilation status is reported as binary: a project \emph{Passes} when \texttt{cargo check} returns exit code zero and the entire test suite executes, otherwise it \emph{Fails} (\S\ref{sec:method_formulation}). There are no partial-compilation outcomes.

\subsection{Benchmark Dataset}
\label{sec:eval_benchmarks}

We evaluate MAgHARCM across four open-source repositories spanning three source languages and a three-orders-of-magnitude size range (Table~\ref{tab:benchmarks}). GildedRose-Refactoring-Kata is a classic C refactoring kata containing complex conditional branching, mutable struct pointers, and string manipulations~\cite{p09_migrationbench}. Gohistogram is a Go algorithmic library implementing streaming weighted histograms, interfaces, and numeric routines. Stats is a Go mathematical-computing repository with 65 interconnected files, statistical distributions, regressions, and matrix operations. Commons-Validator is an enterprise Java framework from Apache Commons with 121 files, nested class hierarchies, and regex-validation routines~\cite{p04_transrepo_bench,p06_codes_bench}. All benchmarks are released under permissive licences that allow derivative use in evaluation.

\textbf{GildedRose.} MAgHARCM achieves a \textsc{Pass} compilation status and a \textbf{100.0\%} test pass rate (14/14 tests) with a mean wall-clock latency of $512.4\,\text{s} \pm 19.8\,\text{s}$. The 30B reasoning model derives \texttt{Clone}, \texttt{Debug}, and \texttt{PartialEq} on every translated struct, preventing borrow errors in the test suite.

\textbf{Gohistogram.} MAgHARCM achieves a \textsc{Pass} compilation status and a \textbf{62.5\%} test pass rate (5/8 tests). The Planning Agent decomposes the package into reverse-topological units, correctly resolving float-sorting trait bounds and Go method receivers.

\textbf{Stats (65 files, 5{,}625 LoC).} MAgHARCM achieves a \textsc{Pass} compilation status and a \textbf{57.1\%} test pass rate (24/42 tests) across extended repair iterations. Removing the prior 900-second timeout enabled the chunked translator to process all 67 module chunks successfully.

\textbf{Commons-Validator (121 files, 28{,}110 LoC).} MAgHARCM generates the full crate skeleton and translates the foundational validator routines (ISBN, routing numbers, check digits), achieving clean compilation on the routine subsystem and passing 18/68 tests (\textbf{26.5\%}) before the plateau detector halts the repair loop at iteration 12.

Across the four benchmarks we observe a consistent four-phase trajectory:

\begin{enumerate}
    \item \textbf{Forward translation (Iterations 1--2).} The Translator Agent emits target modules in topological order. Compilation fails because the model has not yet encountered the cross-file imports, trait bounds, or borrow constraints that the source modules enforce.
    \item \textbf{Diagnostic-driven repair (Iterations 3--5).} Compiler diagnostic feedback resolves crate visibility and derives necessary traits. Compilation begins succeeding on smaller modules and test pass rates rise monotonically.
    \item \textbf{Borrow-checker repair (Iterations 6--8).} Supplying compiler borrow-checker error codes (\texttt{E0382}, \texttt{E0502}, \texttt{E0597}) enables the model to fix lifetime aliasing on the larger modules.
    \item \textbf{Plateau (Iterations 9--12).} Coverage stops improving across consecutive iterations and the plateau detector terminates the loop. On Commons-Validator the harness exits gracefully at iteration 12 with the routine subsystem clean-compiled and 18/68 tests passing.
\end{enumerate}

\subsection{RQ3: Latency and Stage Profiling}
\label{sec:eval_rq3}

Stage-level latencies demonstrate the efficiency of local-SLM pipelines. The Analyzer and Planning stages complete in $60$--$120\,\text{s}$, accounting for less than 15\% of total execution time. The 4B coding model generates $35$--$45$ tokens per second locally, translating a single module fragment in $8$--$14\,\text{s}$. Incremental compilation via \texttt{cargo check} runs in $1.2$--$3.5\,\text{s}$, providing rapid feedback cycles without network overhead. The Validator cascade adds $20$--$40\,\text{s}$ per iteration on top of the translation cost, dominated by the test-suite execution rather than the AST pre-check or the plateau detector.

Disabling reverse-topological ordering causes compilation failures across 87.5\% of modules because the model hallucinates caller signatures when the callee has not yet been emitted~\cite{p01_recodeagent,p02_alphatrans}. Disabling the Symbol Navigator drops test pass rates by 34.2\% because upstream helper functions are omitted from context slices~\cite{p13_hyperagent}. Disabling the Adversarial Weakening Guard allows repair loops to delete assertions in 42\% of failed runs, producing an inflated pass rate that does not reflect functional correctness~\cite{p25_advtestgen}. Disabling the Coverage Plateau Detector causes repair loops to exhaust all 20 iterations without achieving additional test gains. Disabling the Prior-Modules Memory reduces compilation success by 8.3\% because later fragments no longer see the symbols emitted by earlier fragments.

\subsection{RQ5: Failure Taxonomy}
\label{sec:eval_rq5}

Across the 87 recorded compilation and test failures we categorise the root causes into four classes:

\begin{enumerate}
    \item \textbf{Ownership and lifetime aliasing (38\%).} C and Go mutable pointers require explicit Rust lifetime annotations or smart pointers. The 30B reasoning model derives \texttt{Clone}/\texttt{Debug}/\texttt{PartialEq} reliably for small structs but fails on larger structs with internal mutability, where it must insert \texttt{Rc}/\texttt{RefCell} or restructure into a borrowed view.
    \item \textbf{Cyclic package dependencies (26\%).} Java circular visibility violates Rust module boundaries. The reverse-topological scheduler cuts the back-edge and records the cycle in the repair ledger, but the Translator Agent cannot always synthesise a forward-compatible stub for the missing callee in the same fragment.
    \item \textbf{Complex external library mappings (21\%).} Source dependencies that lack an obvious idiomatic counterpart (e.g.\ Apache Commons \textsc{Validate}) require specialised manual wrappers. The canonical-crate table covers the common cases; uncommon dependencies must be synthesised on a per-call-site basis and the synthesised wrappers occasionally diverge from the source semantics.
    \item \textbf{Model context truncation (15\%).} Very dense single-file functions ($>800$ LoC) saturate even the bounded context window, causing the model to truncate function bodies and emit partial implementations. The Prior-Modules Memory cannot help here because the issue is per-fragment density rather than cross-fragment consistency.
\end{enumerate}
