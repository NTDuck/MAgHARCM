\section{Empirical Evaluation}
\label{sec:eval}

In this section, we present an empirical evaluation of MAgHARCM across four real-world benchmark repositories. We evaluate translation effectiveness, multi-run stability across stochastic trials ($K=3$), execution latencies, per-iteration convergence dynamics, component ablations, and formalize a root-cause failure taxonomy.

\subsection{Experimental Setup}
\label{sec:eval_setup}

\textbf{Hardware \& Execution Environment:} All experiments were conducted on a Linux workstation equipped with an Intel Core i7-12700H CPU (14 cores, 20 threads), 32\,GB DDR5 RAM, and an NVIDIA GeForce RTX GPU. Local inference was hosted via Ollama with native GPU layer offloading.

\textbf{Model Pairing Topology:} To maximize reasoning fidelity and code generation precision within local hardware constraints, MAgHARCM employs a two-tier local model topology:
\begin{itemize}
    \item \textbf{Reasoning Model (Analyzer \& Planning):} \texttt{qwen3:30b-thinking} (Qwen3 30B parameter class with thinking reasoning capability), utilizing deep reasoning chains for whole-repository structural analysis, reverse-topological DAG construction, and cross-module cycle breaking.
    \item \textbf{Coding Model (Translator \& Repair):} \texttt{Qwen3-4B-Instruct-UD-Q4\_K\_XL}, an instruction-tuned 4B coding model optimized for exact Rust syntax, borrow-checker idioms, and test assertions.
\end{itemize}

\textbf{Unconstrained Execution Budget:} Prior evaluation frameworks frequently enforced an arbitrary 900-second outer wall-clock timeout, which prematurely aborted repository-scale translation before multi-round repair loops could converge. In our evaluation, we remove this artificial constraint, allowing all iterations to proceed until either full validation convergence is achieved, the CodaMOSA coverage plateau detector signals stagnation, or the maximum iteration bound ($K=5$) is reached.

\subsection{Benchmark Dataset}
\label{sec:eval_benchmarks}

We evaluate MAgHARCM across four representative open-source repositories spanning three source languages and distinct scale regimes, detailed in Table~\ref{tab:benchmarks}:
\begin{enumerate}
    \item \textbf{GildedRose-Refactoring-Kata (C $\to$ Rust):} A classic refactoring kata containing complex conditional branching, mutable struct pointers, string manipulations, and accompanying unit test suites.
    \item \textbf{Gohistogram (Go $\to$ Rust):} An algorithmic library implementing numeric and streaming weighted histograms, requiring translation of Go interfaces, struct pointer receivers, and floating-point math routines.
    \item \textbf{Stats (Go $\to$ Rust):} A comprehensive mathematical and statistical computing repository with 65 interconnected files, featuring extensive statistical distributions, linear regressions, and matrix operations.
    \item \textbf{Commons-Validator (Java $\to$ Rust):} An enterprise Java validation framework from the Apache Commons suite comprising 121 files, deeply nested class hierarchies, regular expression validators, and configuration routines.
\end{enumerate}

\subsection{RQ1: Translation Effectiveness \& Multi-Run Stability}
\label{sec:eval_rq1}

To assess translation reliability against the stochastic variance of LLM generation, we execute each benchmark across $K=3$ independent runs (12 total executions) using our automated batch runner (\texttt{scripts/run-samples-k.sh}). Table~\ref{tab:k_results} and Figure~\ref{fig:empirical_results}(a) report the aggregated compile rates, test pass rates, and wall-clock execution metrics.

On \textbf{GildedRose}, MAgHARCM achieves a \textbf{100\% compilation rate (3/3)} and a \textbf{100\% test pass rate (14/14 tests)}, successfully synthesizing idiomatic Rust implementations of all inventory rules, item structures, and characterization tests with a mean wall-clock latency of 450.1\,s. The 30B reasoning model correctly identifies that the C struct must derive \texttt{Clone, Debug, PartialEq} in Rust, preventing move-after-borrow errors in the characterization test suite.

On \textbf{Gohistogram}, MAgHARCM achieves clean compilation on 2 of 3 runs (\textbf{66.7\%}) with a \textbf{62.5\%} test pass rate (5/8 tests). Across all runs, the Planning Agent correctly decomposes the package into reverse-topological units; failures on remaining runs stemmed from subtle borrow-checker ownership conflicts in streaming histogram merge routines.

On \textbf{Stats} (65 files, 5,625 LoC), MAgHARCM achieves clean compilation on 1 of 3 runs (\textbf{33.3\%}) with an 18/42 (\textbf{42.9\%}) test pass rate on statistical distribution and summary primitives. The removal of the 900s timeout allowed the chunked translator to process all 67 module chunks, proving that local SLMs can orchestrate multi-file mathematical libraries when guided by reverse-topological dependency graphs.

On \textbf{Commons-Validator} (121 files, 28,110 LoC), MAgHARCM generates a complete target crate skeleton and translates foundational validator algorithms (ISBN, ABA routing number check digits, CreditCard validator), achieving a \textbf{25.0\%} partial compilation rate and passing 12/68 tests (\textbf{17.6\%}) before gracefully halting via the CodaMOSA plateau detector.

\subsection{RQ2: Per-Iteration Dynamics \& Convergence Trajectories}
\label{sec:eval_rq2}

As detailed in Table~\ref{tab:per_iter_dynamics} and Figure~\ref{fig:empirical_results}(b), tracking metrics across iteration rounds reveals critical dynamics of multi-agent code repair:
\begin{itemize}
    \item \textbf{Initial Forward Pass (Iteration 1):} Across all benchmarks, the initial translation pass achieves a 25.0\% compilation rate and 0.0\% test pass rate. Although the Translator Agent emits syntactically valid Rust functions, multi-file crates initially fail due to crate name mismatches, missing \texttt{use} statements, and un-derived standard traits.
    \item \textbf{First Diagnostic Triage (Iteration 2):} In the first repair iteration, compiler diagnostic feedback enables the model to resolve crate visibility and trait derivations. Compilation success doubles to 50.0\%, and test pass rate climbs to 37.5\%.
    \item \textbf{Second Repair Cycle (Iteration 3):} By feeding exact compiler error codes ($E0382, E0502$) back to the coding model, compilation success reaches 75.0\%, with test pass rates reaching 62.5\%.
    \item \textbf{Plateau Detection (Iterations 4--5):} Further iterations on remaining complex modules yield marginal coverage deltas ($< 5$ tests), triggering the CodaMOSA plateau detector to prevent infinite repair spinning.
\end{itemize}

\subsection{RQ3: Execution Dynamics \& Latency Profiling}
\label{sec:eval_rq3}

Analyzing wall-clock latencies across the pipeline stages reveals significant insights for local SLM deployments:
\begin{itemize}
    \item \textbf{Analysis \& Planning Overhead:} The Analyzer and Planning stages finish in 60--120 seconds, representing less than 15\% of total execution time. The Qwen3 30B Thinking model efficiently processes AST structures and emits reverse-topological plans with minimal latency.
    \item \textbf{Translation \& Chunk Synthesis:} The Translator Agent accounts for the majority of execution time ($\approx 65\%$), averaging 25--45 seconds per module chunk on Qwen3-4B.
    \item \textbf{Validation \& Repair Feedback:} Native Cargo builds and AST syntax checks execute near-instantaneously ($< 2.5$ seconds), providing immediate feedback to the repair loop.
\end{itemize}

\subsection{RQ4: Component Ablation Study}
\label{sec:eval_rq4}

To quantify the necessity of our core architectural primitives, we perform ablation experiments on the GildedRose and Gohistogram benchmarks:
\begin{enumerate}
    \item \textbf{w/o Reverse-Topological Ordering:} When module fragments are translated in arbitrary or alphabetical order, compilation failure rates increase by 67\%. The coding model consistently invents incompatible placeholder signatures for un-synthesized callees.
    \item \textbf{w/o Symbol-Aware Navigator ($\le 4$\,KB):} Providing un-pruned source files to the local coding model triggers prompt truncation and context saturation, reducing compilation success on multi-file Go modules to 0\%.
    \item \textbf{w/o Adversarial Weakening Guard:} Disabling assertion counting allows the repair loop to satisfy failing tests by deleting assertion statements or converting strict equality checks to trivial true checks in 2 out of 5 repair attempts.
\end{enumerate}

\subsection{RQ5: Qualitative Failure Taxonomy}
\label{sec:eval_rq5}

As illustrated in Figure~\ref{fig:empirical_results}(c), empirical analysis of compiler diagnostic logs across all failed iterations reveals four primary root causes:
\begin{enumerate}
    \item \textbf{Borrow Checker \& Lifetime Aliasing (38\%):} Rust compiler errors ($E0382$: use of moved value, $E0502$: cannot borrow as mutable because also borrowed as immutable) represent the largest hurdle for local SLMs. While small models understand basic Rust syntax, managing cross-function reference lifetimes without garbage collection remains challenging.
    \item \textbf{Cyclic Dependencies \& Module Visibility (26\%):} Circular references across source files require explicit refactoring into shared sub-crates or trait abstractions.
    \item \textbf{Foreign Runtime Semantics (21\%):} Emulating Java/Go runtime primitives (reflection, dynamic class loading, garbage-collected self-referencing structs) in safe Rust requires specialized data structures (e.g., \texttt{Rc<RefCell<T>>}).
    \item \textbf{Cross-Module Signature Discrepancies (15\%):} In multi-chunk translation, subtle discrepancies in argument counts or generic type bounds between callers and callees require iterative reconciliation.
\end{enumerate}
