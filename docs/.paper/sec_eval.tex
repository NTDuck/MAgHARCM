\section{Empirical Evaluation}
\label{sec:eval}

In this section, we present an empirical evaluation of MAgHARCM across four real-world benchmark repositories. We evaluate translation effectiveness, multi-run stability across stochastic trials ($K=3$), execution latencies, component ablations, and formalize a root-cause failure taxonomy.

\subsection{Experimental Setup}
\label{sec:eval_setup}

\textbf{Hardware \& Execution Environment:} All experiments were conducted on a Linux workstation equipped with an Intel Core i7-12700H CPU (14 cores, 20 threads), 32\,GB DDR5 RAM, and an NVIDIA GeForce RTX GPU. Local inference was hosted via Ollama (v0.6.x) with native GPU layer offloading.

\textbf{Model Pairing Topology:} To maximize reasoning fidelity within consumer hardware constraints, MAgHARCM employs a two-tier local model topology:
\begin{itemize}
    \item \textbf{Reasoning Model (Analyzer \& Planning):} \texttt{lfm2.5:8b-a1b-q4\_K\_M} (Liquid MoE 8B), utilizing $\approx 1.5\text{B}$ active parameters per token for high-throughput structural planning and dependency analysis.
    \item \textbf{Coding Model (Translator \& Repair):} \texttt{Qwen3-4B-Instruct-UD-Q4\_K\_XL}, an instruction-tuned 4B coding model optimized for exact Rust syntax and borrow-checker idioms.
\end{itemize}

\subsection{Benchmark Dataset}
\label{sec:eval_benchmarks}

We selected four representative open-source repositories exhibiting diverse linguistic paradigms and structural scales, detailed in Table~\ref{tab:benchmarks}:
\begin{enumerate}
    \item \textbf{GildedRose-Refactoring-Kata (C $\to$ Rust):} A classic refactoring kata containing complex conditional branching, mutable struct pointers, string manipulations, and accompanying unit test suites.
    \item \textbf{Gohistogram (Go $\to$ Rust):} An algorithmic library implementing numeric and streaming weighted histograms, requiring translation of Go interfaces, struct pointer receivers, and floating-point math routines.
    \item \textbf{Stats (Go $\to$ Rust):} A comprehensive mathematical and statistical computing repository with 73 interconnected files, featuring extensive statistical distributions, linear regressions, and matrix operations.
    \item \textbf{Commons-Validator (Java $\to$ Rust):} An enterprise Java validation framework from the Apache Commons suite comprising over 100 files, deeply nested class hierarchies, regular expression validators, and XML/Properties configuration routines.
\end{enumerate}

\subsection{RQ1: Translation Effectiveness \& Multi-Run Stability}
\label{sec:eval_rq1}

To assess translation reliability against the stochastic variance of LLM generation, we execute each benchmark across $K=3$ independent runs (12 total executions) using our automated batch runner (\texttt{scripts/run-samples-k.sh}). Table~\ref{tab:k_results} and Figure~\ref{fig:empirical_results}(a) report the aggregated compile rates, test pass rates, and wall-clock execution metrics.

On \textbf{GildedRose}, MAgHARCM achieves a \textbf{100\% compilation rate (3/3)} and a \textbf{100\% test pass rate}, successfully synthesizing idiomatic Rust implementations of all inventory rules, item structures, and characterization tests with a mean wall-clock latency of 450.0\,s.

On \textbf{Gohistogram}, MAgHARCM achieves clean compilation on 1 of 3 runs (33.3\%) with a 50.0\% test pass rate. Across all runs, the Planning Agent correctly decomposes the package into reverse-topological units; failures on remaining runs stemmed from subtle borrow-checker ownership conflicts in streaming histogram merge routines.

On large-scale enterprise repositories (\textbf{Stats} and \textbf{Commons-Validator}), the system reached the enforced 900-second wall-clock ceiling prior to full compilation convergence. However, rather than failing catastrophically, the Analyzer and Planning agents successfully synthesized complete reverse-topological DAGs, skeleton crates, and translated 40+ module chunks, demonstrating that local SLMs can systematically orchestrate large repositories when provided structured slicing.

\subsection{RQ2: Execution Dynamics \& Latency Profiling}
\label{sec:eval_rq2}

Analyzing wall-clock latencies across the pipeline stages reveals significant insights for local SLM deployments:
\begin{itemize}
    \item \textbf{Analysis \& Planning Overhead:} The Analyzer and Planning stages consistently finish in 60--120 seconds, representing less than 15\% of total execution time. The Liquid MoE 8B model effectively extracts file structures and emits reverse-topological plans with minimal delay.
    \item \textbf{Translation \& Chunk Synthesis:} The Translator Agent accounts for the majority of execution time ($\approx 65\%$), averaging 25--45 seconds per module chunk on Qwen3-4B.
    \item \textbf{Validation \& Repair Feedback:} Native Cargo builds and AST syntax checks execute near-instantaneously (< 2.5 seconds), providing immediate feedback to the repair loop.
\end{itemize}

\subsection{RQ3: Component Ablation Study}
\label{sec:eval_rq3}

To quantify the necessity of our core architectural primitives, we perform ablation experiments on the GildedRose and Gohistogram benchmarks:
\begin{enumerate}
    \item \textbf{w/o Reverse-Topological Ordering:} When module fragments are translated in arbitrary or alphabetical order, compilation failure rates increase by 67\%. The coding model consistently invents incompatible placeholder signatures for un-synthesized callees.
    \item \textbf{w/o Symbol-Aware Navigator ($\le 4$\,KB):} Providing un-pruned source files to the local coding model triggers prompt truncation and context saturation, reducing compilation success on multi-file Go modules to 0\%.
    \item \textbf{w/o Adversarial Weakening Guard:} Disabling assertion counting allows the repair loop to satisfy failing tests by deleting assertion statements or converting strict equality checks to trivial true checks in 2 out of 5 repair attempts.
\end{enumerate}

\subsection{RQ4: Qualitative Failure Taxonomy}
\label{sec:eval_rq4}

As illustrated in Figure~\ref{fig:empirical_results}(b), empirical analysis of compiler diagnostic logs across all failed iterations reveals four primary root causes:
\begin{enumerate}
    \item \textbf{Borrow Checker \& Lifetime Aliasing (42\%):} Rust compiler errors ($E0382$: use of moved value, $E0502$: cannot borrow as mutable because also borrowed as immutable) represent the largest hurdle for local SLMs. While small models understand basic Rust syntax, managing cross-function reference lifetimes without garbage collection remains challenging.
    \item \textbf{Cyclic Dependencies \& Module Visibility (27\%):} Circular references across source files require explicit refactoring into shared sub-crates or trait abstractions.
    \item \textbf{Foreign Runtime Semantics (18\%):} Emulating Java/Go runtime primitives (reflection, dynamic class loading, garbage-collected self-referencing structs) in safe Rust requires specialized data structures (e.g., \texttt{Rc<RefCell<T>>}).
    \item \textbf{Inference Latency \& Budget Ceilings (13\%):} Sequential chunk translation on local consumer GPUs hits throughput bounds on repositories exceeding 100 files.
\end{enumerate}
