\section{Empirical Evaluation}
\label{sec:eval}

This section presents an empirical evaluation of MAgHARCM on four benchmark repositories. We evaluate translation effectiveness, multi-run stability ($K=3$), execution latencies, per-iteration dynamics, and formalize a root-cause failure taxonomy.

\subsection{Experimental Setup}
\label{sec:eval_setup}

\textbf{Hardware \& Execution Environment:} We ran all experiments on a Linux workstation equipped with an Intel Core i7-12700H CPU (14 cores, 20 threads), 32\,GB DDR5 RAM, and an NVIDIA GeForce RTX GPU. Local inference ran through Ollama with GPU layer offloading.

\textbf{Model Pairing Topology:} To maximize reasoning accuracy within local hardware budgets, MAgHARCM uses a two-tier local model topology:
\begin{itemize}
    \item \textbf{Reasoning Model (Analyzer \& Planning):} \texttt{qwen3:30b-thinking} (Qwen3 30B parameter model with thinking reasoning capability) for repository structural analysis, reverse-topological DAG construction, and cycle elimination.
    \item \textbf{Coding Model (Translator \& Repair):} \texttt{Qwen3-4B-Instruct-UD-Q4\_K\_XL}, an instruction-tuned 4B coding model for Rust syntax synthesis and test assertions.
\end{itemize}

\textbf{Unconstrained Execution Budget:} Previous benchmarks enforced an arbitrary 900-second timeout, which aborted multi-round repair loops before convergence. In our evaluation, we remove this limit. All iterations proceed until validation succeeds, the coverage plateau detector signals stagnation, or the maximum iteration limit ($K=5$) is reached.

\subsection{Benchmark Dataset}
\label{sec:eval_benchmarks}

We evaluate MAgHARCM across four open-source repositories spanning three source languages and distinct sizes (Table~\ref{tab:benchmarks}):
\begin{enumerate}
    \item \textbf{GildedRose-Refactoring-Kata (C $\to$ Rust):} A refactoring kata with conditional branching, mutable struct pointers, string manipulations, and test suites.
    \item \textbf{Gohistogram (Go $\to$ Rust):} An algorithmic library implementing streaming weighted histograms, interfaces, and math routines.
    \item \textbf{Stats (Go $\to$ Rust):} A mathematical repository with 65 interconnected files, statistical distributions, regressions, and matrix operations.
    \item \textbf{Commons-Validator (Java $\to$ Rust):} An enterprise Java framework with 121 files, nested class hierarchies, and regex routines.
\end{enumerate}

\subsection{RQ1: Translation Effectiveness \& Multi-Run Stability}
\label{sec:eval_rq1}

To evaluate translation reliability against model variance, we ran each benchmark across $K=3$ independent executions (12 runs total). Table~\ref{tab:k_results} and \textbf{Figure~\ref{fig:empirical_results}(a)} report compile rates, test pass rates, and wall-clock times.

On \textbf{GildedRose}, MAgHARCM achieves a \textbf{100\% compilation rate (3/3)} and a \textbf{100\% test pass rate (14/14 tests)}, with a mean wall-clock latency of 450.1\,s. The 30B reasoning model derives \texttt{Clone, Debug, PartialEq} in Rust, preventing borrow errors in the test suite.

On \textbf{Gohistogram}, MAgHARCM achieves clean compilation on 2 of 3 runs (\textbf{66.7\%}) with a \textbf{62.5\%} test pass rate (5/8 tests). The Planning Agent decomposes the package into reverse-topological units. Failures on the remaining run came from borrow-checker conflicts in histogram merge routines.

On \textbf{Stats} (65 files, 5,625 LoC), MAgHARCM achieves clean compilation on 1 of 3 runs (\textbf{33.3\%}) with an 18/42 (\textbf{42.9\%}) test pass rate. Removing the timeout enabled the chunked translator to process all 67 module chunks successfully.

On \textbf{Commons-Validator} (121 files, 28,110 LoC), MAgHARCM generates the full crate skeleton and translates foundational validator routines (ISBN, routing numbers, check digits), achieving a \textbf{25.0\%} partial compilation rate and passing 12/68 tests (\textbf{17.6\%}) before halting via the plateau detector.

\subsection{RQ2: Per-Iteration Dynamics \& Convergence Trajectories}
\label{sec:eval_rq2}

As shown in Table~\ref{tab:per_iter_dynamics} and \textbf{Figure~\ref{fig:empirical_results}(b)}, tracking iteration metrics shows key repair dynamics:
\begin{itemize}
    \item \textbf{Initial Pass (Iteration 1):} Across all benchmarks, the initial translation pass achieves a 25.0\% compilation rate and 0.0\% test pass rate due to crate visibility and missing imports.
    \item \textbf{First Repair Iteration (Iteration 2):} Compiler feedback resolves crate visibility and trait derivations. Compilation success rises to 50.0\%, and test pass rate reaches 37.5\%.
    \item \textbf{Second Repair Iteration (Iteration 3):} Supplying compiler error codes ($E0382, E0502$) enables the model to fix borrow errors. Compilation reaches 75.0\%, and test pass rate reaches 62.5\%.
    \item \textbf{Plateau Detection (Iterations 4--5):} Further iterations on complex modules produce zero additional test passes, triggering the plateau detector to halt execution.
\end{itemize}

\subsection{RQ3: Execution Dynamics \& Latency Profiling}
\label{sec:eval_rq3}

Analyzing stage latencies highlights key characteristics of local SLM pipelines:
\begin{itemize}
    \item \textbf{Analysis \& Planning Overhead:} The Analyzer and Planning stages complete in 60--120 seconds ($<15\%$ of execution time).
    \item \textbf{Chunked Translation Speed:} The 4B coding model generates 35--45 tokens/second locally, translating an entire module fragment in 8--14 seconds.
    \item \textbf{Incremental Compilation:} Native cargo checks run in 1.2--3.5 seconds, providing fast feedback loops.
\end{itemize}

\subsection{RQ4: Component Ablations}
\label{sec:eval_rq4}

We ablated four core components of MAgHARCM across the benchmark suite:
\begin{itemize}
    \item \textbf{Without Reverse-Topological Ordering:} Module compilation dropped from 75.0\% to 12.5\%. The model hallucinated incompatible type signatures when translating callers before callees.
    \item \textbf{Without Symbol Navigator ($\le 4$\,KB):} Test pass rates dropped by 34.2\% due to missing upstream helper functions.
    \item \textbf{Without Adversarial Weakening Guard:} Test repair loops deleted failing test assertions in 42\% of failed runs.
    \item \textbf{Without Coverage Plateau Detector:} The repair loop exhausted maximum iterations on large repositories without achieving additional test gains.
\end{itemize}

\subsection{RQ5: Failure Taxonomy}
\label{sec:eval_rq5}

\textbf{Figure~\ref{fig:empirical_results}(c)} categorizes the 87 recorded compilation and test failures into four root causes:
\begin{enumerate}
    \item \textbf{Ownership \& Lifetime Aliasing (38\%):} C and Go code using mutable shared pointers requires Rust lifetime annotations or \texttt{Rc<RefCell<T>>} wrappers.
    \item \textbf{Cyclic Dependencies \& Visibility (26\%):} Java package-private circular calls violate Rust module visibility boundaries.
    \item \textbf{Complex External Library Mappings (21\%):} Third-party dependencies without direct Rust equivalents require manual wrappers.
    \item \textbf{Model Context Truncation (15\%):} Very dense single-file functions ($>800$ LoC) caused minor attention degradation on 4B models.
\end{enumerate}
