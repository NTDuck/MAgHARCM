\section{Conclusion and Next Steps}
\label{sec:conclusion}

We presented MAgHARCM, a Go implementation of the ReCodeAgent
architecture wired against a local Ollama backend with
\texttt{lfm2.5:8b-a1b-q4\_K\_M} MoE as the reasoning model and
\texttt{Qwen3-4B-Instruct} as the coding model. MAgHARCM preserves the
four-agent decomposition (Analyzer $\rightarrow$ Planning
$\rightarrow$ Translator $\rightarrow$ Validator), adds a tree-sitter
native LSP provider with ABCoder MCP fallback, and runs end-to-end on
a single host with no API access.

We exercised the harness on Sample 1 (GildedRose C$\rightarrow$Rust)
across four independent runs. Compilation succeeded in 100\% of the
runs. The iter3 run, which exhausted the iteration budget and emitted
the full assertion-failure diagnostic, achieved a 4/7 = 57\% test
pass rate. The three failing assertions (negative \texttt{sell\_in}
backstage pass, Sulfuras quality preservation, and elapsed-time
backstage pass) all trace to a single hallucination in the
Translator's Rust output -- the model wrote a clamp-to-50 branch
where the source C writes a zero-out branch. We classify this as a
failure of the Translator's per-batch diagnostic triage rather than a
failure of the four-agent decomposition: the Validator correctly
flagged the failure, but the coding model was unable to repair the
branch under the iteration budget.

We also exercised the harness on Sample 2 (Oxidizer/stats Go
$\rightarrow$ Rust) and observed a clean ceiling failure: the
single-shot Translator returns an empty response when prompted with
517 translation fragments, leaving the target tree empty and the
Validator with a vacuous 0/0 result. This is the failure mode that
NEW-PRIM-23, the chunked Translator primitive described in
Section~\ref{sec:method}, is designed to address. Samples 3 and 4
remain deferred.

\subsection{Next Steps}

Three concrete next steps:

\begin{enumerate}
\item \textbf{Implement NEW-PRIM-23 (chunked Translator).}
Replace the single-shot Translator with the bounded-batch loop in
Algorithm~\ref{alg:chunked}. The loop groups fragments into batches
of size $B$ (initial default $B=8$, to be tuned against the 4B
model's effective context window), per-batch-compiles after each
batch, and runs the global Validator once at the end. This is the
single most important next step because it unblocks Sample 2 and
unblocks any future sample whose fragment count exceeds the
single-shot ceiling.

\item \textbf{Rerun Samples 2, 3, and 4 with the chunked Translator.}
Sample 2 (Oxidizer/stats) is the immediate beneficiary. Sample 3
(AlphaTrans commons-validator, Java $\rightarrow$ Python) needs a
Python toolchain wired into \texttt{config.yml} before it can be
exercised; Sample 4 (Oxidizer/gohistogram) needs the harness pointed
at it. Once all four samples have been exercised end-to-end under
the chunked Translator we can publish a complete compile/test table
to replace the partial Table~\ref{tab:headline}.

\item \textbf{Add per-iteration diagnostic triage to the Translator.}
The Sample 1 iter3 failures show that the 4B coding model cannot
prioritise between an E0425 \emph{cannot find function} batch, an
E0382 \emph{borrow of moved value} batch, and the later
behavioural-assertion failures once all three are present in the
same diagnostic. A diagnostic-clustering pre-pass on the Validator
report (group errors by file and rank groups by failure rate) is the
likely remediation; we expect this to move the Sample 1 behavioural
test pass rate from 57\% to the 80--90\% range on the same model.

\end{enumerate}

The harness, the run logs, and the four-agent prompt templates are
checked into the MAgHARCM repository under
\texttt{cmd/}, \texttt{internal/agents/}, and
\texttt{.artifacts/} so that future runs are reproducible end-to-end.
