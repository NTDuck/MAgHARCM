\section{Introduction}
\label{sec:intro}

Software migration across programming languages is a frequent requirement in software engineering. Organizations regularly migrate legacy codebases written in C, C++, Java, or Go to modern systems programming languages such as Rust. This transition removes critical memory safety vulnerabilities including buffer overflows, use-after-free errors, and data races~\cite{szekeres2013sok,p58_syzygy,p56_rust_ffi_verification}. Modern target languages also improve runtime efficiency and long-term maintainability. However, manual repository migration remains slow, expensive, and error-prone~\cite{khajeh2019automated,p46_muller_migration}.

\subsection{The Repository Migration Bottleneck}
\label{sec:intro_bottleneck}

Large Language Models (LLMs) translate isolated functions and synthesize unit tests with high accuracy~\cite{chen2021evaluating,roziere2020transcoder,p43_llm_testgen_survey}. But migrating an entire multi-file software repository introduces distinct technical barriers. 

First, production codebases contain interconnected files with shared structs, type definitions, and call graphs. Translating files independently causes missing symbol declarations and build failures~\cite{p03_codeplan,p62_repograph}. 

Second, source languages like C and Go frequently use circular imports. Translating these patterns directly into strict systems languages like Rust violates ownership, lifetime, and module visibility constraints~\cite{siddiq2024oxidizer,p05_oxidizer,p07_rustrepotrans}. 

Third, supplying an entire repository in one prompt exhausts the context window. This causes hallucinations, missing function bodies, and truncated code on local models~\cite{p18_deepseekcoder,p21_qwen2_5coder}. 

Fourth, without rigorous validation, generative models produce code that compiles syntactically but fails behavioral tests. Uncontrolled repair loops often remove failing assertions to report false success~\cite{ibrahimzada2026recodeagent,p01_recodeagent,p25_advtestgen}.

\subsection{Limitations of Existing Approaches}
\label{sec:intro_limits}

Existing automated migration methods fall into two categories: rule-based transpilers and neural models. Rule-based transpilers such as \textsc{C2Rust}~\cite{c2rust,p38_c2rust}, \textsc{CXGO}, and \textsc{JavaC2Rust}~\cite{p59_javac2rust_tooling} use deterministic AST transformations. They preserve semantics on supported subsets, but they emit unidiomatic code with raw pointers and unsafe blocks~\cite{p50_rav1d_c2rust_case,p51_libexpat_c2rust_case}. 

Neural translation systems such as \textsc{TransCoder}~\cite{roziere2020transcoder} and \textsc{AlphaTrans}~\cite{yang2024alphatrans,p02_alphatrans} operate on single functions without repository orchestration. Multi-agent systems such as \textsc{ReCodeAgent}~\cite{ibrahimzada2026recodeagent}, \textsc{MetaGPT}~\cite{hong2023metagpt,p11_metagpt}, and \textsc{ChatDev}~\cite{qian2023chatdev,p12_chatdev} showed that specialized agents improve translation over monolithic prompts. However, existing multi-agent pipelines depend on large closed-source cloud models with high token costs and privacy risks.

\subsection{The MAgHARCM Framework}
\label{sec:intro_magharcm}

To enable reliable repository migration on local hardware, we introduce \textbf{MAgHARCM} (\textbf{M}ulti-\textbf{Ag}ent \textbf{H}arness for \textbf{A}rchaeology-guided \textbf{R}epository-scale \textbf{C}ode \textbf{M}igration). MAgHARCM is an open-source translation engine built in Go on CloudWeGo Eino. It executes on local quantized models through Ollama.

MAgHARCM coordinates four specialized agents over an explicit workflow. The Analyzer Agent inspects source AST structures, checks dependency mappings, and uses M\"uller Strategy Selection~\cite{muller2022towards} to determine migration scope. The Planning Agent extracts AST fragments, builds a cycle-free Reverse-Topological Dependency DAG, rewrites build manifests into canonical target crates, and schedules implementation steps. The Translator Agent emits target code using Chunked Translation, bounded by a Symbol Navigator and compact Prior Memory to prevent context saturation. The Validator Agent executes a multi-stage validation cascade comprising AST syntax checks, compiler build validation, test suite execution, an Adversarial Weakening Guard, and a Coverage Plateau Detector.

\subsection{Key Contributions}
\label{sec:intro_contributions}

The primary contributions of this paper are:
\begin{enumerate}
    \item \textbf{Modular Multi-Agent Architecture for Local SLMs:} We formulate and implement MAgHARCM, a 4-agent migration harness optimized for local quantized model pairs (a 30B reasoning model paired with an instruction-tuned 4B coding model).
    \item \textbf{Bounded Context Assembly \& Reverse-Topological Scheduling:} We introduce reverse-topological dependency scheduling with back-edge removal, paired with a Symbol Navigator ($\le 4$\,KB) and Prior Memory ($\le 4$\,KB) to prevent context overflow.
    \item \textbf{Multi-Stage Validation \& Adversarial Defense:} We design a validation cascade that combines AST syntax checks, compiler feedback, and an adversarial test-weakening guard that halts execution if test assertions are removed.
    \item \textbf{Empirical Evaluation \& Failure Taxonomy:} We evaluate MAgHARCM on four benchmark repositories across $K=3$ stochastic runs without artificial timeouts. We present an empirical failure taxonomy showing borrow-checker lifetime errors (38\%) and cyclic references (26\%) as key bottlenecks.
\end{enumerate}
